EXECUTIVE SUMMARY
=================
This audit covers the SmartERP Laravel application spanning approximately 42 controllers,
40+ models, and a routes file with ~200 routes. Findings are organized by severity.

Total Issues Found:
  Critical:  5
  High:     14
  Medium:   18
  Low:       9

The most severe problems are: (1) nearly all routes are completely unprotected by the
'auth' middleware, (2) the 'All' middleware authorization check is trivially bypassed,
(3) the Payroll update deletes all receiveAdvance transactions for the month and not just
payroll-created ones, (4) the balance calculation for bank transfers uses the wrong sign,
and (5) the opening-stock mechanism writes to a hardcoded stock_id=1 record with no
referential integrity guard.

Issue #2:
  Severity: Critical
  Title: Almost all routes are outside the auth middleware group
  Description: The route file defines a Route::group(['middleware' => 'auth']) block
               (lines 45-51) that contains zero actual routes – it is an empty shell.
               Every operational route (/admin, /user, /role, /attendance, /payroll, etc.)
               is declared outside any middleware group. Protection relies 100% on
               controller constructors calling $this->middleware(['auth', 'all']).
               If a single controller forgets to call $this->middleware() in its constructor,
               that entire module is publicly accessible. This is a systemic architectural
               risk. Best practice is to wrap routes in the group so route-level enforcement
               exists independent of controller code.
  Expected: All authenticated routes should be within Route::middleware('auth')->group(...)
  Actual: Empty auth group; all routes are top-level.
  File(s): routes/web.php:45-51 and entire file

  Description: storeTransfer() (line 737-742) computes the from-bank balance as:

OBSERVATIONS & RISKS
====================

1. AUTHORIZATION MODEL COMPLETENESS
   The permission system uses a permissions table with permission_role pivot. However,
   hasPermission() (User.php:46) issues a raw DB query on every permission check. For a
   page with 5+ authorize() calls, this is 5+ queries per request. Consider caching the
   user's permissions at login.

2. ATTENDANCE MODULE (Keep this untouched)
   The attendance module is non-functional (dd() in index()) and depends on an Access
   Database file at a hardcoded Windows path. This entire module needs to be redesigned
   for production deployment.

3. STOCK BALANCE TRACKING APPROACH
   Stock levels are computed by summing stock_items.quantity (IN records) minus
   stock_items.quantity (OUT records) with no denormalized balance column. For large
   datasets with many stock movements, every stock balance query scans all history.
   Consider adding a running balance or snapshot table.

4. PIPE-SEPARATED FOREIGN KEYS
   The products.material_id and products.stage_ids columns store pipe-separated integers
   (e.g., '12|45|67'). This violates 1NF, prevents proper JOIN operations, and requires
   PHP-side string parsing. The existing product_materials table is the correct normalized
   approach; the pipe-separated columns appear to be a legacy holdover.

5. DELIVERY RETURN STOCK ADJUSTMENT
   When a delivery return is stored, adjustStock() creates a NEW stock record for the
   returned goods. However, this returned stock goes into general stock (not back to a
   specific PTC or order). The system does not update the original delivery's stock
   items. This means the original delivery_item quantities remain unchanged even after
   a return. Reports on "delivered quantity" will overstate actual net delivery.

6. PTC (PROCESS TRAVEL CARD) COMPLEXITY
   The PTC module reuses the stocks and stock_items tables for issuance, receiving,
   and stage movements. All records are distinguished by is_ptc_master, ptc_id, and
   stock_type columns. This table design creates very complex queries (seen in ptcShow())
   with multiple self-joins and left-joins. Consider extracting PTCs into dedicated tables
   (ptc_records, ptc_issuances, ptc_receivings) for clarity and query performance.

7. MISSING API RATE LIMITING
   The AJAX endpoints (ajaxPM, ajaxPT, ajaxBank, ajaxBalance, ajaxOrder, etc.) have no
   rate limiting. A malicious authenticated user could hammer these endpoints to enumerate
   all data or cause DoS-level query load.

8. PAYROLL DOES NOT ENFORCE DOUBLE-PAYMENT PREVENTION
   PayrollController::create() checks if payroll exists and redirects to edit. However,
   PayrollController::store() does NOT check for existing payroll before inserting. If
   a user bypasses the create() redirect (e.g., by posting directly), duplicate salary
   transactions will be created.

9. PRODUCT OPENING STOCK ON EDIT DELETES AND RECREATES
   ProductController::updateStageSpecificOpeningStock() (line 339) deletes ALL opening
   stock entries for a product and recreates them. If any other process has added
   stock_items with stock_id=1 for this product independently, those will also be deleted.

10. NO AUDIT TRAIL FOR FINANCIAL CORRECTIONS
    When transactions are updated or payroll is reprocessed, the original records are
    simply overwritten or deleted. There is no audit log of what the original values were.
    The spatie/activitylog package is installed (visible in User.php) but is not configured
    for financial models (Transaction, Stock, Order, Purchase).

11. CUSTOMER BALANCE CALCULATION INCONSISTENCY
    The customer balance is calculated differently in:
    - TransactionController::ajaxBalance() (lines 397-427): filters deliveries vs payments
    - CustomerController::detail(): uses transaction repository
    - EmployeeController::detail() (line 227): filters out salary transactions from balance
    These inconsistencies could result in different balance figures shown in different parts
    of the UI for the same customer/employee.

12. FOREIGN KEY CONSTRAINTS
    The migration files reviewed do not add explicit FOREIGN KEY constraints between:
    - stock_items.stock_id -> stocks.stock_id
    - stocks.ptc_id -> stocks.stock_id (self-referential)
    - stocks.order_id -> orders.order_id
    - transactions.payee_id -> employees/vendors/customers (polymorphic, hard to constrain)
    Without FK constraints, orphaned records can accumulate silently.
