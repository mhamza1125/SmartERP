FIX #1: Issue #14 — Payroll update deletes ALL receiveAdvance transactions
---------------------------------------------------------------------------
File: app/Http/Controllers/PayrollController.php

ORIGINAL PROBLEM:
PayrollController::update() deleted ALL transactions of type 'receiveAdvance'
for employees in the target month, including manually-entered loan repayments
that were not created by the payroll process.

IMPLEMENTED FIX:

FIX #2: Issue #12 — Impossible compound condition for customer GV balance
--------------------------------------------------------------------------
File: app/Http/Controllers/TransactionController.php (ajaxBalance, ~line 418)

ORIGINAL PROBLEM:
The condition `if ($gv->credit == 0 && $gv->credit === null)` is logically
impossible — a value cannot simultaneously equal 0 (loose) AND be null (strict).
This meant ALL general vouchers were treated as Debit Vouchers, so Credit
Vouchers (which should decrease customer receivable) were misclassified and
overstated the customer balance.

IMPLEMENTED FIX:
Replaced the impossible condition with `if ($gv->credit === null)`.
When a Credit Voucher is stored: credit=null, debit=0.
When a Debit Voucher is stored: credit=0, debit=null.
Checking credit===null correctly identifies Credit Vouchers.

DATABASE / MIGRATION NOTES: None.

TESTING STEPS:
1. Go to Transactions → New General Voucher for a Customer.
2. Create a Debit Voucher (increases receivable) for PKR 5,000.
3. Create a Credit Voucher (decreases receivable) for PKR 2,000.
4. Open the customer's ledger / balance via ajaxBalance.
5. Net balance from these vouchers should be +5,000 - 2,000 = +3,000 on the
   receivable side. Before the fix it would show +7,000.

EXPECTED RESULT: Customer balance correctly reflects Credit Vouchers reducing
the receivable by the cc_amount value.

FIX #6: Issue #8 — updateTransfer finds paired transaction by wrong bank_id
---------------------------------------------------------------------------
Files: app/Http/Controllers/TransactionController.php,
       database/migrations/2026_06_16_000001_add_transfer_pair_id_to_transactions_table.php,
       app/Models/Transaction.php

ORIGINAL PROBLEM:
updateTransfer() tried to find the paired transaction using:
  bank_id = original transaction's bank_id (the FROM bank)
But the paired (inflow) transaction has the TO bank's bank_id, which is
different. This query would either return null (pair not updated) or, if two
transfers from the same bank existed on the same date, update the wrong record.

IMPLEMENTED FIX:
1. Added nullable `transfer_pair_id` column to transactions via migration.
2. storeTransfer() now links both transactions to each other:
     Transaction::update(['transfer_pair_id' => $getId2]) for $getId1
     Transaction::update(['transfer_pair_id' => $getId1]) for $getId2
3. updateTransfer() first tries to find the paired transaction by transfer_pair_id
   (deterministic). If null (legacy records created before this fix), it falls
   back to a heuristic: same date, debit not null, credit null — the inflow side.
4. After a successful update, pair_ids are re-synced in case the record changed.

DATABASE / MIGRATION NOTES:
Migration adds nullable column — zero impact on existing records.
Existing transfers (created before this fix) will use the fallback heuristic on
first edit; after one edit their pair_id is saved and future edits use the fast path.

TESTING STEPS:
1. Create two bank-to-bank transfers on the same day from the same source account.
2. Edit the first transfer (change amount or date).
3. Verify ONLY that transfer's paired inflow entry is updated (the second transfer
   should remain unchanged).
4. Edit the second transfer.
5. Verify its paired entry updates correctly.

EXPECTED RESULT: Each transfer edits only its own paired transaction, regardless
of how many other transfers exist on the same date from the same bank.


FIX #7: Issue #35 — DeliveryReturn update doesn't re-adjust stock
-----------------------------------------------------------------
Files: app/Http/Controllers/DeliveryReturnController.php,
       database/migrations/2026_06_16_000002_add_source_id_to_stocks_table.php,
       app/Models/Stock.php

ORIGINAL PROBLEM:
DeliveryReturnController::update() updated the return header and return items
but did NOT update the stock adjustment entries that were created in store().
Changing return quantities left the stock entries from the original store call
in place, creating a stock discrepancy (stock records showed old quantities
while return items showed new quantities).

IMPLEMENTED FIX:
1. Added nullable `source_id` column to stocks table to store the delivery_return_id
   when table_name = 'delivery_returns'.
2. adjustStock() now accepts an optional $deliveryReturnId parameter and saves it
   as source_id on the new stock record.
3. store() passes $returnId as the source_id to adjustStock().
4. update() now:
   (a) Finds the existing return stock via table_name='delivery_returns' AND
       source_id = $id (the delivery_return_id).
   (b) Deletes its stock_items and the stock record itself.
   (c) Updates the return header and items.
   (d) Calls adjustStock() with the new quantities to create fresh stock entries.

DATABASE / MIGRATION NOTES:
Migration adds nullable source_id — zero impact on existing records.
Existing delivery returns (created before this fix) will have source_id=NULL on
their stock records; the update() method will skip the stock reversal for these
legacy records (no existing return stock found to delete). This is safe — the
stock discrepancy existed before and is not made worse; only returns created
AFTER this fix will have fully reversible stock adjustments.

TESTING STEPS:
1. Create a delivery and then a delivery return for 10 units of a product.
2. Check stock: available quantity should increase by 10.
3. Edit the delivery return and change the quantity to 6.
4. Check stock again: available quantity should now reflect +6, not +10.
5. Verify the delivery_return_items table shows qty=6.

EXPECTED RESULT: Stock levels accurately reflect the updated return quantity after
editing a delivery return.


FIX #8: Issue #42 — Opening stock hardcoded to stock_id=1
----------------------------------------------------------
File: app/Http/Controllers/ProductController.php

ORIGINAL PROBLEM:
Both ProductController::store() and updateStageSpecificOpeningStock() hardcoded
'stock_id' => '1' for opening stock entries. If the record at stock_id=1 is
ever deleted or the database is rebuilt, opening stock writes silently orphan or
fail with an FK violation.

IMPLEMENTED FIX:
Added private helper `getOpeningStockId()` that:
1. Checks if stock_id=1 exists — returns 1 if so (fully backward compatible).
2. If stock_id=1 is missing, searches for a stock with stock_no='OPENING-STOCK'
   and table_name='opening_stock'.
3. If that is also missing, creates a new "Master Opening Stock Record" and
   returns its ID.
Both store() and updateStageSpecificOpeningStock() now call this helper instead
of hardcoding '1'.

DATABASE / MIGRATION NOTES:
No schema change needed. Existing data at stock_id=1 is completely unaffected;
getOpeningStockId() returns 1 as long as that record exists.

TESTING STEPS:
1. Create a new product with opening stock quantities.
2. Verify the stock_items records created have stock_id=1 (assuming that record
   exists).
3. To test the fallback: temporarily rename stock_no of stock_id=1 in the DB,
   then create another product — verify a new OPENING-STOCK record is created
   and stock_items link to it.
4. Edit the product's opening stock — verify the stock_items update correctly.

EXPECTED RESULT: Opening stock entries are always linked to a valid stock record,
preventing orphaned foreign keys even if stock_id=1 is removed.

FIX #12: Issue #17 — Payroll store/update lack DB::transaction wrapping
-----------------------------------------------------------------------
File: app/Http/Controllers/PayrollController.php

ORIGINAL PROBLEM:
PayrollController::store() and update() issued multiple transaction INSERT/DELETE
statements inside a foreach loop with no DB::transaction() wrapper. A connection
drop or DB error mid-loop would leave payroll in a partial state (some employees
paid, others not).

IMPLEMENTED FIX:
Wrapped the entire foreach (and the delete-then-insert block in update()) inside
DB::transaction(). If any statement fails, all changes are automatically rolled back.
PHP references (&$transactionCount, &$totalAmount) allow return values to propagate
out of the closure.
